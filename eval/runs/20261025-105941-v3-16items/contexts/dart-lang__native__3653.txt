## Description
From the [documentation](https://clang.llvm.org/docs/AutomaticReferenceCounting.html#arc-runtime-objc-retainautoreleasedreturnvalue), I *think* we can just replace all our calls to `objc_retain` with this function. If the reference was not recently autoreleased, this is the same as an `objc_retain` call. But if it was autoreleased, then this essentially promotes the autoreleased reference to a strong reference.

This would reduce the number of autoreleased references we hold, helping to mitigate https://github.com/dart-lang/sdk/issues/61129 / https://github.com/dart-lang/native/issues/3652 (though it's still not a complete solution, because the ObjC APIs the user is calling could autorelease their own internal references).

Thanks for the tip @brianquinlan

    It's not so simple as just calling `objc_retainAutoreleasedReturnValue`: There is a special protocol between caller and callee.
    
    The called ObjC function that returns the object will get the return address from the stack and look at the following machine instructions to see if it fits a certain pattern (see [here](https://github.com/opensource-apple/objc4/blob/cd5e62a5597ea7a31dccef089317abb3a661c154/runtime/objc-object.h#L1060)). This is also described e.g. [here](https://theapplewiki.com/wiki/Automatic_Reference_Counting#arm64)
    
    So we cannot just use a FFI calls to `objc_msgSend` and then another FFI call to `objc_retainAutoreleasedReturnValue` with the returned value -- it will not take it out of autorelease pool.

[2026-09-21 08:23Z, 34d ago] mraleph commented:
    The landed PR does not actually do anything because there is a protocol between `objc_autoreleaseReturnValue` and `objc_retainAutoreleasedReturnValue` which you need to follow for hand-off to succeed. 
    
    See [the code](https://github.com/apple-oss-distributions/objc4/blob/fb265098298302243cd7eeaa1f63f0ba7786dd9a/runtime/NSObject.mm#L2335-L2342), more specifically [`prepareOptimizedReturn`](https://github.com/apple-oss-distributions/objc4/blob/fb265098298302243cd7eeaa1f63f0ba7786dd9a/runtime/objc-object.h#L1612-L1673) and [`acceptOptimizedReturn`](https://github.com/apple-oss-distributions/objc4/blob/fb265098298302243cd7eeaa1f63f0ba7786dd9a/runtime/objc-object.h#L1676-L1724).
    
    TLDR is that on ARM64  `objc_autoreleaseReturnValue` will put a tuple of `(obj, return-address)` into the TLS and `objc_retainAutoreleasedReturnValue` will check whether `return-address` corresponds to its call-site. There are also some corner-cases (e.g. classes which intercept `retain` / `release` messages are handled specially) where these methods will look at instructions at the call-site to detect a special marking instructions (e.g. `mov fp, fp` on ARM64). 
    
    I don't think we can fully satisfy the protocol without some low-level surgery in the FFI implementation in the VM.  
    
    PS. Additional data point. If you take the PR and revert all the changes except changes in the tests - those tests will still pass. Which seems to indicate that the PR does not do anything.
[2026-09-22 01:51Z, 34d ago] liamappelbe commented:
    Ok, that's a much bigger change then. We'd need to add a new flag similar to `isLeaf` to `@Native` etc, and then change the trampoline based on that flag. We would only really need to enable that flag for `objc_msgSend` and co (and only if they return an object pointer with a +0 reference).
    
    As for *how* we change the trampoline:
    - The straightforward option would be to call `objc_retainAutoreleasedReturnValue` inside the trampoline, which is fine as long as the caller knows that this means the reference is now +1 instead of +0, and must be caught in a Dart wrapper object. As long as we're careful about version skew between VM/FFIgen/package:objective_c, this should be ok. A bit risky tho.
    - A fancier approach would be to try to make the `objc_retainAutoreleasedReturnValue` work by making the trampoline transparent, so that from Dart code it looks like we are directly calling `objc_msgSend`. This seems like it would be extremely difficult.
    
    Overall I'm not sure it's worth it. Better to just wrap every `objc_msgSend` call in an autorelease pool. Seems like a lot of effort to go to to save a few ns.
