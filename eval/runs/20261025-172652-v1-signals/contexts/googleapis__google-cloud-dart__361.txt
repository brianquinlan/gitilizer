## Description
### Context & Problem

`google_cloud_compute_v1` (landed in #323) is currently configured in `librarian.yaml` (lines 281–293) without `specification_format: discovery`. As a result, `librarian` derives `google/cloud/compute/v1` and generates `google_cloud_compute_v1` from `google/cloud/compute/v1/compute.proto` (`SpecificationFormat: protobuf`).

However, Compute Engine does not use `google.longrunning.Operations`. In `compute.proto`, long-running operations return `google.cloud.compute.v1.Operation` and are annotated with `google.cloud.operation_service` extensions (`ZoneOperations`, `RegionOperations`, `GlobalOperations`, `GlobalOrganizationOperations`), which `internal/sidekick/parser/protobuf.go` does not parse into `api.Method.OperationInfo` or `DiscoveryLro`.

By contrast, in `googleapis/librarian`:
- `internal/serviceconfig/sdk.yaml:436-438` maps `google/cloud/compute/v1` to `discovery: discoveries/compute.v1.json`.
- `internal/sidekick/parser/discovery/lro.go` (`lroAnnotations`) populates `api.Method.DiscoveryLro` (`PollingPathParameters`) and injects service-scoped `getOperation` poller methods (`IsLroPoller: true`) when `modelConfig.Discovery` (`*api.Discovery`) is configured via `CommonDiscovery` (`internal/config/discovery.go`, as used by `internal/librarian/rust/codec.go:96-108` and `internal/librarian/swift/generate.go:149-161`).
- PR #345 (`google_cloud_dns_v1`) already introduces `sources.discovery` and `specification_format: discovery` in `librarian.yaml` for Dart.

### Proposed Solution

1. **Support `SpecDiscovery` and `CommonDiscovery` in `googleapis/librarian` (`internal/librarian/dart/codec.go` & `internal/config/`)**:
   - Update `toModelConfig` in `internal/librarian/dart/codec.go` (lines 31–66) to accept `config.SpecDiscovery` and resolve `SpecificationSource = svcConfig.Discovery` (`"discoveries/compute.v1.json"`, matching `internal/librarian/rust/codec.go:46-53`).
   - Add `Discovery *CommonDiscovery` (`yaml:"discovery,omitempty"`) to `config.DartPackage` and map `library.Dart.Discovery` (`OperationID` and `Pollers`) to `modelConfig.Discovery` in `internal/librarian/dart/codec.go` (matching `internal/librarian/rust/codec.go:96-108`).
2. **Update `google_cloud_compute_v1` in `librarian.yaml`**:
   - Switch `google_cloud_compute_v1` to `specification_format: discovery` with `roots: [discovery, googleapis]` and configure `dart.discovery` poller mappings:
     ```yaml
     dart:
       discovery:
         operation_id: .google.cloud.compute.v1.Operation
         pollers:
           - prefix: compute/v1/projects/{project}/zones/{zone}
             method_id: .google.cloud.compute.v1.zoneOperations.get
           - prefix: compute/v1/projects/{project}/regions/{region}
             method_id: .google.cloud.compute.v1.regionOperations.get
           - prefix: compute/v1/projects/{project}/global
             method_id: .google.cloud.compute.v1.globalOperations.get
           - prefix: compute/v1/locations/global
             method_id: .google.cloud.compute.v1.globalOrganizationOperations.get
     ```
3. **Wire `DiscoveryLro` Poller Generation in `sidekick/dart` (for #28)**:
   - Use the injected `IsLroPoller` (`getOperation`) mixin and `api.Method.DiscoveryLro.PollingPathParameters` (`project`, `zone`, `region`, `operation`) in `internal/sidekick/dart/annotate.go` so Compute Engine mutations (`Instances.insert`, `Disks.insert`, etc.) expose typed LRO polling helpers alongside standard `google.longrunning.Operation` methods (#28).

### Acceptance Criteria

- [ ] `internal/librarian/dart/codec.go` in `googleapis/librarian` supports `specification_format: discovery` (`SpecificationSource = svcConfig.Discovery`) and `dart.discovery` (`CommonDiscovery` pollers).
- [ ] `google_cloud_compute_v1` in `librarian.yaml` uses `specification_format: discovery` (`discoveries/compute.v1.json`) with `zoneOperations`, `regionOperations`, `globalOperations`, and `globalOrganizationOperations` pollers configured.

[2026-10-08 21:59Z, 17d ago] kevmoo commented:
    @brianquinlan Yes, exactly! Manual polling via `operationsService.get` works and is perfectly usable, but it isn't idiomatic compared to the `op.wait()` polling helpers generated for services returning standard `google.longrunning.Operation`.
    
    Because `internal/sidekick/parser/protobuf.go` doesn't currently parse the `google.cloud.operation_service` annotations (`ZoneOperations`, `RegionOperations`, etc.) used in `compute.proto`, `sidekick` treats Compute operations as standard RPC responses. This forces clients to write manual `while(true)` polling loops with explicit `Future.delayed` and `status == Operation_Status.done` checks, as seen in `address_test.dart`.
    
    If we switch Compute Engine to `specification_format: discovery` in `librarian.yaml` and configure the `CommonDiscovery` LRO pollers, `internal/sidekick/parser/discovery/lro.go` will correctly map these to `api.Method.DiscoveryLro`. This gives us the necessary AST data to wire up idiomatic polling helpers for Compute Engine in `sidekick/dart` (resolving #28), bringing it to parity with how Rust and Swift handle Compute LROs.
