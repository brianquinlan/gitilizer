## Description
## Summary

For an error received as JSON, `ServiceException.fromHttpResponse` puts the HTTP status code into `ServiceException.status.code`. The `google.rpc.Code` the service reported, which the JSON error carries by name in `status`, is dropped.

`Status.code` is documented as "an enum value of `google.rpc.Code`", and the rest of the package already treats it that way:

- The gRPC error mapping in `google_cloud_pubsub` (`_mapGrpcError`) puts the gRPC code there. Its comment says this matches how `fromHttpResponse` fills it for REST errors, but it doesn't.
- `ExponentialRetry.isRetryable` reads `status.code`, for example `ConflictException(:final status) => status?.code == 10`. Over REST that value is 409, so an `ABORTED` error is never retried.

## Why it matters

Several `google.rpc.Code`s share an HTTP status, and only the name tells them apart:

| HTTP | `status` | for example (Firestore `commit`) |
|---|---|---|
| 400 | `FAILED_PRECONDITION` | "the stored version (…) does not match the required base version (…)" |
| 400 | `INVALID_ARGUMENT` | "Invalid transaction." |
| 409 | `ABORTED` | "Aborted due to cross-transaction contention. …" |
| 409 | `ALREADY_EXISTS` | "Document already exists: …" |

These are real responses from `google_cloud_firestore_v1` 0.5.5 `commit` calls. As things stand, a client can't tell a transaction it should retry (`ABORTED`) from a write that can never succeed (`ALREADY_EXISTS`), or a stale precondition from a malformed request, except by parsing the message.

## Reproduction

```dart
import 'package:google_cloud_rpc/exceptions.dart';
import 'package:google_cloud_rpc/retry.dart';
import 'package:http/http.dart' as http;

void main() {
  const body = '{"error": {"code": 409, "message": "Aborted due to cross-transaction contention.", "status": "ABORTED"}}';
  final e = ServiceException.fromHttpResponse(http.Response(body, 409), body);
  print(e.status!.code); // 409, expected 10
  print(const ExponentialRetry().isRetryable(e)); // false, expected true
}
```

## Proposed fix

In `fromHttpResponse`, set `Status.code` to the `google.rpc.Code` named by the error's `status`, and keep the HTTP status code when `status` is missing or unknown. `ServiceException.statusCode` still has the HTTP status code.

This changes `status.code` for JSON errors that name their code (400 becomes 3, and so on), so code that compared it with an HTTP status would need `statusCode` instead. Errors without a `status`, such as Cloud Storage's JSON API errors, are unaffected. PR: #382.

Versions: google_cloud_rpc 0.6.0 (`main` has the same code), google_cloud_firestore_v1 0.5.5.
