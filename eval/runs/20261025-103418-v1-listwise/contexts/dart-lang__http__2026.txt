## Description
Fixes #2021.

`StreamHandler._handleEndOfStreamRemote` removed a stream from `_openStreams` as soon as the peer's END_STREAM moved it from `HalfClosedLocal` to `Closed`, even if the application had not read the stream's incoming messages yet. The stream's entry in the connection-level `ConnectionMessageQueueIn` was left behind, so a later `Connection._terminate` skipped the stream (`StreamHandler.onTerminated` only walks `_openStreams`) and then failed:

```
Failed assertion: '_stream2messageQueue.isEmpty': is not true.
  ConnectionMessageQueueIn.onTerminated
  Connection._terminate
```

When END_STREAMs arrive in the other order (ours after the peer's), `_endStream` moves the stream to `Closed` without removing it. It stays in `_openStreams` until both of its queues are done and `_cleanupClosedStream` runs, so termination closes it normally. This change makes the peer-END_STREAM path behave the same way, which is what the TODO at that line was asking for.

### Tests

`terminate-with-undrained-closed-stream--{server,client}-ends-first` in `transport_test.dart` runs the scenario from the issue over the in-memory transport, in both END_STREAM orders, with the server never reading the stream's messages:

| Order | Before | After |
|---|---|---|
| server END_STREAM first | ❌ assertion above | ✅ |
| client END_STREAM first | ✅ | ✅ |

The first commit adds only the test, so it can be checked out to see the failure. `dart test` in `pkgs/http2` passes (256 tests), and `dart analyze --fatal-infos` reports no issues.
