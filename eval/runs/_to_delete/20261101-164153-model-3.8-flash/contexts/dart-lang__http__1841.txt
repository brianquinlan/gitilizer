## Description
it is generally recommended that on 503, if the server responds with the `Retry-After` header we should respect that and if it's not present we should default back exponential backoff.

Is this something that coud be considered to be added directly into the `RetryClient`, so we have that as default behaviour?

I am asking this because we already retrying [503 by default](https://github.com/dart-lang/http/blob/2cb6c12966e18abc11a0217a8b613742849a29ea/pkgs/http/lib/retry.dart#L182C1-L182C4).

    Another way to do this without breaking the existing API is to keep delay(int retryCount) as the default backoff policy and add a separate opt-in callback for response-aware delays. For example:
    
    `Duration? Function(BaseResponse response, int retryCount)? retryDelay`
    
    The default implementation would continue using the current exponential backoff, while callers that need server-controlled retry timing can provide a function that reads Retry-After and returns the appropriate delay. This preserves compatibility for existing users while allowing Retry-After support without changing the meaning of delay.
    That keeps the change focused and avoids forcing all retry users to depend on BaseResponse in the existing callback.
