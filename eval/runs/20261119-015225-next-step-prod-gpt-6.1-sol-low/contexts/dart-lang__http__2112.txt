### Summary

Fixes two `Http2Client` performance regressions against 3.1.0 introduced in 3.2.0. They were found with [`package:http_client_benchmarks`](https://github.com/brianquinlan/http_client_benchmarks) and bisected over every `pkgs/http2` commit since `http2-v3.1.0`:

| Scenario | 3.1.0 | `master` / #2031 | Introduced by | This PR |
| --- | --- | --- | --- | --- |
| `download-cancel`: cancel a response after 256 KiB, then make one more request (median, lower is better) | 0.97 ms | 26.3 ms | `be2b51f` #2029 (fixed 4 MiB stream window) | 4.4?4.5 ms |
| `upload-1mib-sequential`: 20 sequential 1 MiB uploads (higher is better) | 27.7 MB/s | 20.7 MB/s | `23f8574` #1999 (1 MiB DATA frames, together with Nagle) | 109?115 MB/s |

All numbers are from a Linux Cloudtop (x64, 48 vCPU), loopback, Dart 3.14.0-dev (JIT), 7 trials + 2 warmup.

1. **A cancelled response held up the connection.** With #2029's fixed 4 MiB stream window, the server has sent up to 4 MiB of a response before the client's `RST_STREAM` reaches it (the benchmark measured at least 1.8 MiB unread). TCP can't skip bytes, so all of that must be received, decrypted and discarded before the response to the next request on the same connection. That costs about 25 ms here, where Dart's TLS manages about 100 MB/s. On an emulated 100 ms / 200 Mbit/s link it added about 55 ms to the next request. On a slow mobile link it would be far worse, because there the drain is bounded by the link's bandwidth.
2. **`Http2Client` never disabled Nagle's algorithm** (see the section below). Since #1999, `Http2Client` honours the peer's `SETTINGS_MAX_FRAME_SIZE`, so an upload to a Go server (1 MiB max frame size) goes out as a single 1 MiB DATA frame. The short tail of that write is then held back by Nagle until the earlier segments are acknowledged. Meanwhile the server delays its acknowledgement (by 40 ms on Linux), because it can't do anything with the frame until the tail arrives. So nearly every upload paid that stall.

### Changes

- **`lib/src/http2_client.dart`**
  - Sets `SocketOption.tcpNoDelay` on every connection, as `dart:io`'s `HttpClient` and `HttpServer` do.
  - Each stream's receive window now starts at 256 KiB (`SETTINGS_INITIAL_WINDOW_SIZE`) instead of 4 MiB and grows up to 4 MiB as the body is read. The connection window stays at 16 MiB.
- **`lib/src/flowcontrol/window_handler.dart`**
  - `IncomingWindowHandler.stream` takes an optional `maxWindowSize`.
  - When the handler sends a WINDOW_UPDATE (once half the window has been processed), it also adds the current window size to the increment, up to `maxWindowSize`, so the window doubles.
  - Data only counts as processed while the stream's listener isn't paused, so the window only grows while the body is actually being read. Backpressure (#2029) still holds: a paused body holds at most the current window.
- **`lib/src/connection.dart`, `lib/src/streams/stream_handler.dart`**
  - Pass an internal `maxStreamWindowSize` from `ClientConnection` (not exported) to new streams.
  - There is no public API change. `ClientTransportConnection.viaSocket` and `ServerTransportConnection` behave as before.
- **`CHANGELOG.md`**
  - Adds entries under `3.2.2-wip`.
  - Adds an entry for `TCP_NODELAY`.

Not changed: outgoing DATA frames still use the peer's `SETTINGS_MAX_FRAME_SIZE`. I also tried capping them at 16 KiB: with `TCP_NODELAY` it made `upload-large-buffered` 16% slower (122 vs 145 MB/s), so the 1 MiB frames from #1999 are fine once Nagle is off.
